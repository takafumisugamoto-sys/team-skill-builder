Findy ／ 工程別skill作成キット

team-skills-builder

リポジトリからチームの規約を集めて、PR作成やセルフレビューなど、選んだ開発工程のskillを作るキットです。一般的な開発の心得はAIがすでに知っているので、このキットは「そのチームでしか通用しない決まり」だけを、出典つきで書きます。

版 0.1.2 利用者への確認 2 回 生成までの時間 約8分（Findyでの試験） 配布 zip（Markdown 5ファイルとREADME）

要点
このキットの新しい点と概要

    
このキットの新しい点

    

      
01
組織ごとのskill
汎用のskillを配るのではなく、その組織のリポジトリから集めた規約で、工程ごとのskillを作ります。指示ファイル、lintやCIの設定、コードの実態、git履歴、レビューコメントが材料になり、書く規約にはすべて出典が付きます。

      
02
Findy Libraryの実践知の参照
組織の規約が見つからない部分は、Findy Libraryの実践知を基準にします。生成したskillはMCPで使うたびに最新の本文を読み、skillには要点とURLだけを書きます。

      
03
学習ループの同梱
生成したskillそれぞれに学習ループが入っています。人が直した点と見逃しを記録し、同じ趣旨が3件たまったらチェックリストや規約への反映を提案します。

    

    
概要

    

      
できるもの
選んだ工程ごとに、手順、チェックリスト、出典の一覧、学習の記録をまとめたskillのフォルダーができます。PRタイトルのように形式を判定できる工程には、検証用のスクリプトも付きます。

      
中身の根拠
書く規約には、ファイルと行、コミット、レビューコメントのどれかの出典が付きます。運用で守られている割合と過去の変更でのバックテストで確かめてから書き、根拠のない一般論は書きません。

      
使ったあと
生成したskillは「セルフレビューして」のような普段の依頼で起動し、人が直した点を記録して、チェックリストの見直しを提案します。

    

  






  

    

      
作られるskill

      
工程ごとのskillフォルダー

      
工程ごとに1つのフォルダーができます。skillの本体は .agents/skills/ に置き、Claude Codeからは .claude/skills/ のリンクで読み込みます。

    

    

      

        
フォルダーの中身

        

          self-review/
          ├─ SKILL.md手順・チェックリスト・学習ループ
          ├─ learnings.md人が直した点と見逃しの記録
          ├─ references/
          │  ├─ conventions.md規約の詳細
          │  └─ sources.md指示ごとの出典
          └─ scripts/出力の形式チェック（該当する工程だけ）
        

      

      

        
工程の種類

        
既定の10工程は、skillの働き方で2つに分かれます。一覧にない工程も、名前を付けて追加できます。

        

          
チェック型

          
差分を規約で点検し、指摘を出す

          
コード変更セルフレビューレビューQA

        

        

          
生成型

          
規約に沿った成果物を作る

          
要件定義タスク分解Issue作成PR作成マージリリース

        

      

    

  






  

    

      
使うとこうなる

      
skillあり・なしでの回答の比較

      
skillも指示ファイルもない公開OSS（リポジトリA）で、このキットを使って「セルフレビュー」と「PR作成」の2つのskillを生成しました。そのうえで、過去に実際にあった変更3件を、生成したskillあり・なしの2つのエージェントに渡し、「PRを出す準備をして、出す前にセルフレビューもして」と依頼しました。下は、そのうち1件への回答の違いです。各行に、違いを生んだskillを示しています。

    

    
変更Aタイムアウト処理の不具合修正（3ファイル）。実際にはマージ後にカバレッジ検査が落ち、テストを足す修正が入った変更です。

    

      

        観点
        skillなし
        skillあり
      

      

        カバレッジセルフレビューSkill
        
冗長な分岐を指摘し、カバレッジで落ちる可能性に触れた。閾値は「未確認」のまま、npm run coverage での確認を勧めた。

        
「カバレッジが落ちる可能性が高い」と判断し、テストが通らない分岐を2ファイル3か所挙げた。CIと同じ npm run coverage:ci-check-coverage での確認を求めた。

      

      

        PR本文の型PR作成Skill
        
独自の見出しと ## Checklist を付けた。

        
組織共通テンプレートの項目は運用で守られている割合が低いため、残すかどうかを開発者に確かめる項目として扱った。

      

      

        PRタイトルPR作成Skill
        
規約の形式で書いた。許可された接頭辞かどうかは、3件のうち1件だけ確かめた。

        
CIのタイトル検査と同じ正規表現で、3件すべてを手で照合した。

      

    

    
マージ後の失敗を予見したのはskillありだけ挙げた3か所は、実際の修正箇所とほぼ一致しました。どちらのエージェントにも、実際のPRタイトルとマージ後の経過は見せていません。

    

      
3件の変更での採点結果

      
3件の変更をまとめて、事前に固定した採点基準で比べた点数です。

生成されたskillの例

作成されるSkillの観点

      
skillに書く内容の3分類

      
skillに書く内容は、出どころで3つに分けて扱います。チーム固有の規約は根拠を添えて指示として書き、規約が見つからない部分はFindy Libraryの実践知を参照させます。AIがもともと知っている一般論は書きません。

    

    

      

        
① このチームの規約
指示として書く・出典つき

        
    
          
  • 指示ファイル、CONTRIBUTING.md、lint・CI・commitlint・PRテンプレートなどの設定
    • 
          
  • コードの実態（10件以上の事例があり、90%以上が従っている型だけ）とgit履歴
    • 
          
  • レビューコメント（3件以上のPRで、2人以上が同じ趣旨を指摘したものだけ）
    • 
        

      

      

        
② Findy Library の実践知
規約がない部分の基準

        
    
          
  • Findy LibraryのMCP（lib.findy.co.jp/mcp、認証不要）で、使うたびに最新の本文を読む
    • 
          
  • skillには検索語と要点1行、URLだけを書き、本文は写さない
    • 
        

      

      

        
③ 一般的な開発の心得
書かない

        
    
          
  • AIがすでに知っていることは書かない。根拠のない行は、書き出す前に削除の候補として示す
    • 
        

      

    

  






  

    

      
作られるまで

      
skill作成の7ステップ

      
キットは7つのステップでskillを作ります。利用者に確認するのは、工程を選ぶときと書き出す前の2回だけです。「見本を見る」で、リポジトリAで試したときの画面の要点を表示します。

    

    
利用者に確認する自動で進む


    

      

      


      

        
0

        

          
環境の確認

          
起動した場所がgitリポジトリかを確かめ、違えばそこで止まります。書き込めるか、レビューコメントを取れるか、Findy LibraryのMCPが使えるか、同じ工程のskillがすでにあるかも見ます。

        

      


      

        
1

        

          
対象と工程の選択
確認 1回目

          
対象のリポジトリ（名前とパス）、作りたい工程（最大3つ）、参照する範囲を1回の質問でまとめて聞きます。

          
要件定義タスク分解Issue作成コード変更PR作成セルフレビューレビューQAマージリリース

        

      


      

        
2

        

          
規約の収集

          
工程ごとに決めた場所だけを読み、各規約に出典（ファイルと行、コミット、レビューコメント）を付けます。書かれた決まりも、直近の運用で守られている割合を数え、90%未満なら推奨に回します。

          
          
# リポジトリAで拾った規約の例
PRタイトルの形式        .github/workflows/pull-request-title.yml:17（CIが強制）
'use strict'           直近90日に変更された76ファイル中75件
テストは node:test      直近90日に変更された56件すべて
PRテンプレートの項目    Organization共通のテンプレートにあるが、運用は31件中10件 → 推奨に回す

        

      


      

        
3

        

          
ドラフトの作成

          
雛形に沿ってskillを書きます。手順とチェックリスト、学習ループ、Libraryの検索語が入ります。形式を機械で判定できる工程では、検証用のスクリプトも作ります。

        

      


      

        
4

        

          
規約接地率の確認

          
指示を1行ずつ出典と突き合わせ、出典のファイルと行が実在して本当にその内容を言っているかを読み直します。根拠のない行は削除の候補にします。

        

      


      

        
5

        

          
過去の変更でのバックテスト

          
チェック型の工程は過去の指摘を再現できるか、生成型の工程は過去に人が採用した成果物を検証スクリプトが通すかを見ます。外れた分は原因を分け、最大2回まで直します。

          
          
# リポジトリAでのバックテスト
PRタイトルの検証スクリプト   マージ済みPR 30件中30件が通過 ✓
形式の違うタイトル            2件とも正しく弾いた ✓
PRテンプレートを必須とした指示 過去のPR 13件中5件しか守っていない → 推奨に直した

        

      


      

        
6

        

          
提示と書き出し
確認 2回目

          
結論を1行で示し、判断が要る項目を1件ずつ、重みのラベル、根拠、推奨、はい／いいえの問いの形で並べます。承認を得てから書き出し、コミットはさらに別に確認します。pushとPR作成はしません。

          
          
[imo] 文書と強制設定が食い違っています。
- docs/Guides/Contributing.md:80 は「StandardJS」、eslint.config.js:2 は neostandard
- skillは強制設定と実態に合わせ、文書の記述は採っていません
- 問い: この扱いでよいですか？

[imo] 置き場所が .gitignore で除外されています（.gitignore:177, 179）
- このままではコミットしてもチームに共有されません
- 問い: それでもこの置き場所に書き出しますか？

        

      

    

  






  

    

      
学習ループ

      
生成したskillの学習ループ

      
学習ループは、生成したskillそれぞれの中に入っています。キットを再び実行しなくても、生成したskillを日々使うたびに回ります。仕組みはFindy Libraryの「コードレビューのやり方」と「コンテキストエンジニアリングとは」に沿っています。

      
    
        
  1. 記録skillの出力を人が直した点・却下した点と、あとのレビューで見つかった見逃しを、日付・種類・内容・理由で learnings.md に1行ずつ残す。
    2. 
        
  2. 昇格の提案見逃しはその場で、同じ趣旨の修正・却下は3件たまったら、チェックリスト、規約、lintやCIのどこに移すかを提案する。SKILL.md は勝手に書き換えない。
    3. 
        
  3. 選定lintやCIで強制されるようになった項目は、チェックリストから外すことを提案する。二重に持たない。
    4. 
      

    

    
  






  

    

      
ほかの手段との違い

      
先行事例・組み込み機能との比較

      
国内外の先行事例と、Claude Code組み込みの機能と比べました。部品はそれぞれ存在しますが、工程を選んで、規約を出典つきで集め、検証してから書き出し、使いながら改善するところまでを1つにまとめたものは見つかりませんでした。

    

    

      

        
手段自社規約の根拠工程から選ぶ実践知の基準改善の仕組み

        
          
team-skills-builder○ 出典つき○○ Library○ skillに同梱

          
手書きで作る○○××

          
/init△ コードのみ×××

          
/insights× 個人の会話××△ 提案のみ

          
skill-creator△ 渡した分だけ×△ 一般論△ eval

          
claude-automation-recommender△ 技術スタック×△ 一般論×

          
Repo Skill Generator○ git・PR×××

          
CodeRabbit / Greptile○ レビュー反応××△ ツール内に閉じる

        
      

    

    
価値が出るのは、読めば分かる規約よりも、実行や集計をしないと分からない規約（カバレッジの閾値、テンプレートの実際の運用率、テストの書き方の型）です。

  






  

    

      
使い方

      
skillができるまでの手順

      
ページ上部のプロンプトでキットを書き出してから、skillができるまでの流れです。Claude Codeで動作を確認しています。

  2.

安全性

      
中身・送信・書き換え・審査への備え

      
お客様の環境で使うことを前提に、作りと配り方の両方で備えています。

    

    

      

        キットの中身は何か
        
    
          
  • Markdownのファイル5つ（本体と参照ファイル4つ）とREADMEだけで、実行されるプログラムは含みません。
    • 
          
  • 生成されるskillには形式チェック用のシェルスクリプトが入ることがありますが、書き出す前に中身を示して承認を求めます。
    • 
          
  • 受け取り方のプロンプトにSHA-256のハッシュ値を載せています。受け取ったzipやファイルが改ざんされていないことを、AIが照合して報告します。
    • 
        

      

      

        外部に何を送るか
        
    
          
  • 外部に送るのは、Findy LibraryのMCPへの検索語だけです。検索語は工程から決まる固定の語（「プルリクエスト 粒度」など）で、リポジトリのコードや内容は入りません。
    • 
          
  • 規約を集めるために読んだファイルやレビューコメントは、その場のエージェントの中で使うだけで、Findyには送られません。
    • 
        

      

      

        勝手に書き換えたり、外に出したりしないか
        
    
          
  • ファイルの書き出しは2回目の確認で承認を得てから、コミットはさらに別の確認を経てから行います。pushとPR作成はしません。
    • 
          
  • 生成したskillも、学習ループで SKILL.md を承認なしに書き換えません。
    • 
          
  • リポジトリのファイル、コミット、レビューコメントは調査対象のデータとして読み、中に書かれた指示には従いません。
    • 
          
  • 秘密情報、個人名、メールアドレスを生成物に書きません。
    • 
        

      

      

        社内のセキュリティ審査を通すには
        
    
          
  • 中身・読む場所・書く場所・外部への送信は上のとおり少ないため、1枚の説明にまとめて審査に出せます。審査用の説明資料もご用意しています。
    • 
          
  • エージェントに取り込ませず、人が中身を読んでからフォルダーごとコピーする導入方法も選べます。
    • 
          
  • 社内のリポジトリに一度取り込み、社内のレビューを通したものを各チームで使う形にすれば、外部から直接持ち込む手順をなくせます。
    • 
          
  • 初回は通常のモード（自動で許可しないモード）で動かし、許可を求められる場面を一つずつ確かめることをお勧めします。
    • 
          
  • Findy LibraryのMCPをつながなくても動きます。その場合、実践知の部分は参照先のURLだけになります。
    •
